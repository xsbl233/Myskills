# 业界新技术洞察

将“技术是什么、如何工作”连接到“哪些项目真实采用、项目实际怎样运行、技术具体做了什么并产生什么效果”。默认中文输出，保留可检索的英文术语。实际工作流程、技术作用与效果、实现伪代码和输入输出示例必须按项目组织。默认不再要求独立的部署教程、新旧技术完整对比或项目复现章节；用户明确要求时再补充。

## 确定调研范围

- 用户指定技术或项目时，以其为中心；未指定技术但提供领域时，先检索候选技术及其工程证据，再选取符合目标的对象。连领域和目标都缺失时，询问一个范围问题。
- 记录调研截止日期、目标场景、技术版本和“新颖”的依据。用户未指定时间窗口时，以近两年的关键进展为检索起点，必要时追溯起源；不要把最近发布的介绍文章当作技术首次出现。
- 区分新概念、新算法、已有技术的新工程实现和新应用场景。交代其成熟度，例如论文原型、公开预览、稳定发布或有证据的生产采用。
- 默认选取 2–3 个有代表性的真实项目做深度分析；用户指定数量或深度时遵循其要求。优先选择场景或实现方式有差异、工作流程与实现材料充分的项目。证据不足时减少数量并说明缺口，不凑项目。
- 技术洞察默认交付分析报告，伪代码和示例用于解释实现。用户要求实际运行或复现时再执行，并明确区分示意、预期结果与实际运行结果。

### 查找项目之前确认大方向

在查找、筛选该技术的具体采用项目之前，先确认用户希望关注的应用领域、业务场景或技术方向，不能仅凭技术名称自行决定项目范围。

- 若用户已明确指定方向，或此前已确认且本次仍适用，沿用并简述该范围，无需重复询问。用户只给出技术名称不等于确认了应用方向；指定项目仅确认这些项目的范围，不代表允许向其他方向扩展。
- 方向不明确时，用一个简短问题请用户选择或补充；可给出 2–3 个与该技术相关的候选方向，并说明各自关注点，允许用户选择多个方向或明确要求跨领域调研。
- 等待用户答复后，再启动具体项目检索与筛选；不能将默认选项、用户沉默或等待超时视为确认。等待期间可以整理技术定义与通用原理，必要时做用于形成候选方向的概览检索，但不先行选择项目。
- 如果已确认方向内的项目证据不足，说明缺口，并在跨方向扩展前向用户确认，不自行用其他领域项目补足数量。

在报告范围中记录已确认的方向；后续项目的选择与分析均围绕该范围展开。

## 检索与证据

新技术调研需要实时检索。优先原始论文、官方技术文档、版本公告、项目源码、维护者发布的设计文档和基准测试。二手文章可用于发现线索，关键技术结论应回到一手材料。无法联网时说明时效限制，依据用户材料分析，不声称已经验证最新状态。

对每个候选项目确认：

1. 项目身份、官方仓库或产品页面，以及采用该技术的直接证据。相似名称、依赖列表中的间接依赖或营销提及不足以证明实际采用。
2. 采用范围、对应版本或提交，以及具体实现入口。区分实验分支、演示项目与已发布功能；生产采用需要单独证据。
3. 可访问的实际工作流程、源码或实现说明、调用示例和效果证据。没有公开源码的商业项目可以分析，但必须说明内部实现的可验证边界；不能用通用算法猜测冒充项目的真实实现。

在定义、采用事实、实现细节、数值和比较结论附近附上可访问的来源链接。源码尽量链接固定提交下的文件与行号；论文标注版本或发布日期，网页记录访问日期。明确区分“来源报告”“源码推断”“本次实测”；冲突来源注明版本、条件或日期差异，无法消解时保留争议。

## 解释技术

先用简明语言定义技术、要解决的问题、适用与不适用边界，以及与容易混淆的概念的关系。再解释原理：输入与输出、核心组件、关键算法或机制、执行阶段、状态或数据如何流动、优势来源及其代价。

将机制与既有瓶颈联系起来；需要时给出公式、最小例子或原理图，但不要用术语堆砌替代解释。通用原理与某个项目的实现选择分开描述。

提供采用项目概览表，包含项目、场景、采用位置、版本或提交、成熟度与证据链接，然后逐项目展开以下结构。

## 每个项目的固定分析结构

### 1. 项目实际工作流程

简述项目解决的问题、目标场景与版本，附上真实采用该技术的证据。随后按实际执行顺序解释从输入到输出的完整处理链路，包括关键组件、调用关系、数据或状态变化，以及该技术介入的具体阶段。

必须给出与该项目对应的 Mermaid 工作流程图：输入或任务入口 → 实际处理阶段 → 结果输出。突出该技术所在节点，标注关键数据或控制关系。离线任务使用数据输入和产物输出；异步、缓存、批处理、回退等只在真实存在且影响理解时展示。

图中节点应对应实际组件或阶段，并说明源码或文档依据。不要以通用原理图代替项目工作流，也不要以安装、启动步骤代替运行过程。未知或推断路径需明确标注。

### 2. 该技术具体做了什么，产生什么效果

围绕项目中的具体步骤回答：

- **作用位置**：哪个组件在何时调用该技术，接收哪些数据或状态，输出交给谁。
- **具体操作**：技术对数据、计算、存储、通信或决策做了什么处理，解决了该步骤的什么问题。避免仅写“优化性能”“提升效率”。
- **实际效果**：通过什么机制产生可观察的功能、质量、延迟、吞吐、资源或成本变化；说明适用条件、限制和代价。

有可信量化结果时，给出指标、单位、测试条件、项目版本、基线和来源，区分官方报告、第三方测试与本次实测。只比较同口径数据，不把项目整体收益全部归因于该技术，不把速度提升当成质量提升。缺少量化证据时说明“未找到可验证的量化结果”，保留有证据的定性效果，并将推断单独标记。

仅在解释作用或效果需要时简述不使用该技术的路径或已有方案。替代基线不能冒充项目真实旧实现，也不必扩展为独立的新旧方案全量对比章节。

### 3. 该技术在项目中的实现伪代码

每个项目给出一段针对其实现的伪代码，覆盖技术生效的关键逻辑，以及必要的上下游调用上下文。伪代码应能与工作流程图的节点对应，并注明依据的源码文件、函数、版本或实现文档。

- 明确输入参数、类型或数据结构、输出结果，以及会改变的状态。
- 展开该技术的核心运算、分支、循环或状态更新，不能仅用 `apply_technology(input)` 之类黑盒调用替代核心机制。
- 对辅助组件可以抽象，但要解释辅助函数的职责。只保留影响理解的异常、终止或回退逻辑。
- 区分项目真实行为和为便于解释省略的工程细节；标明“依据源码简化”或“依据公开设计重建”。伪代码不是可直接执行的代码，不声称已运行。
- 若实现未公开且证据不足，明确无法给出经核实的项目实现伪代码。可以附上清楚标记的概念性伪代码，注明假设与未知部分，不能把它当作该项目实现。

### 4. 输入输出示例与过程演示

每个项目至少给出一组具体、足够小且与上述伪代码一致的输入输出示例，说明这是技术模块的输入输出还是项目整体的输入输出。优先使用项目公开示例；自行构造的例子标为“教学示例”，不要暗示来自真实运行。

示例包含：

1. **输入**：具体字段、数据、配置及必要的初始状态；涉及张量或结构化数据时注明形状、类型和字段含义。
2. **关键中间步骤**：沿伪代码展示技术如何处理这组输入，解释关键中间值、选择或状态变化。
3. **输出**：具体结果、结构和含义，说明如何进入后续流程。必要时展示状态更新或副作用。
4. **效果对应**：指出示例体现了哪项作用。技术仅优化计算或存储而不改变结果时，明确输出可能相同，变化在执行过程或资源消耗；不能用教学例子证明性能提升。

确定性逻辑需核对中间值和结果一致；随机、模型生成或依赖外部服务的结果标为“一种可能输出”或“预期输出结构”，注明影响因素，不伪造精确结果。必要时补充一个边界或回退例子，但不为凑数量添加无关样例。

## 报告组织与交付检查

默认顺序：调研范围与日期 → 技术定义 → 核心原理 → 采用项目概览 → 项目 A 的完整分析 → 项目 B 的完整分析（按需继续）→ 跨项目结论与来源。

跨项目结论总结适用场景、成熟度、收益边界、落地门槛和待验证问题；不同项目的测试数字不能直接合并为统一排名。篇幅受限时优先减少项目数，保留每个项目内部的完整链路；仍无法覆盖的部分明确列为缺口。

交付前核对：

- 项目所属大方向已由用户指定或确认，项目检索与筛选未越过该范围。
- 定义与原理能解释技术为何起效，而非只有概念介绍。
- 每个项目有真实采用证据及版本，实际工作流程包含从输入到输出的 Mermaid 图。
- 每个项目明确说明技术介入位置、具体操作、效果与限制，量化结论有可比条件和证据。
- 每个项目提供实现伪代码与输入输出示例；无法核实的实现明确列出缺口，不以猜测补齐。
- 流程图、技术作用、伪代码、中间步骤和输出相互一致，并保持在同一个项目章节内。
- 教学示例、来源结果、预期输出和本次实测没有混淆；没有用小例子或无依据的数字证明性能收益。
- 默认报告不再包含独立部署教程、新旧方案完整对比或复现指南，除非用户另有要求。
