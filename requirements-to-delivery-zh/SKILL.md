# 从需求到交付

推动软件需求从原始意图走向经过测试的交付结果。保持每项需求与设计、实现及验证证据之间的可追踪关系。

## 基本规则

- 制定修改方案前，先检查仓库说明、现有架构、相关代码、测试及工作区状态。
- 将用户已有修改视为有效内容，避免修改与需求无关的部分。
- 持续维护需求清单和开发计划；新证据改变原有判断时及时更新。
- 仅询问会实质影响范围、行为、架构、兼容性、安全、数据或验收结果的问题。合并相关问题，并在适当时给出推荐默认方案。
- 不要实现存在重大歧义的需求；如条件允许，在等待对齐时继续处理不受影响的工作。
- 明确说明合理且低风险的假设，并将其记录在需求清单中。
- 发现并调用适用的已安装 skill 完成专业开发或测试工作。完整阅读选中的 skill，说明使用原因并遵循其要求。只选用覆盖任务所需的最小 skill 集合。
- 每完成一个完整开发步骤就立即验证，不要将所有测试推迟到最后。
- 未提供验证证据或仍有未验证区域时，不得宣称任务完成。

## 阶段一：拆解需求并完成对齐

1. 检查相关源代码、文档、配置、数据结构、测试及当前上下文。
2. 将需求拆分为 `REQ-01` 等原子需求编号。每项需求记录：
   - 预期行为和用户价值；
   - 输入、输出、状态和业务规则；
   - 功能边界、失败行为及边界场景；
   - 受影响的用户、接口、数据、集成及兼容性约束；
   - 适用的安全、性能、可访问性、可观测性及可维护性要求；
   - 可以测试的明确验收标准；
   - 状态：已确认、基于假设或等待问题确认。
3. 找出相互矛盾的要求、缺失的决策、隐藏依赖和范围外事项。
4. 在依赖相关决策的开发开始前，与用户对齐重大不确定项。如果不存在重大疑问，直接说明并继续，不要提出形式化问题。
5. 建立简洁的追踪表：

   `需求 -> 设计/模块 -> 实现步骤 -> 测试/证据`

## 阶段二：制定开发计划

编辑代码前，制定可以执行的详细计划，其中包括：

- 实现顺序及步骤依赖关系；
- 架构和数据流影响；
- 模块边界、职责及公共接口；
- 适用的数据模型、API、配置、迁移和兼容性变更；
- 适用的错误处理、安全、日志、性能及回滚方案；
- 预计修改的文件或代码区域；
- 各模块的测试策略及端到端流程测试策略；
- 每个步骤的完成标准和验证命令。

按照完整模块或行为切片划分步骤，使每一步都可以独立验证。规划工具可用时，仅将一个步骤标记为进行中。仓库证据推翻原有假设时，及时修改计划并解释原因。

## 阶段三：逐步实施开发

针对每一个计划步骤：

1. 再次确认关联的需求编号和验收标准。
2. 检查涉及的确切代码路径和测试。
3. 遵循项目约定，实现完成当前步骤所需的最小完整改动。
4. 在同一步骤中新增或更新测试。
5. 避免无依据的抽象和范围扩张。除非影响正确性，否则将新发现的后续工作单独记录。
6. 仅在当前步骤通过验证门禁后，更新需求及计划状态。

专业开发 skill 明确适用时调用它，但仍需负责将其输出整合进总体计划和需求追踪表。

## 阶段四：验证每个开发步骤

每个实施步骤完成后，按照由窄到宽的顺序执行相关检查：

1. 格式化、代码检查、类型检查、结构校验或编译等静态检查；
2. 变更模块的单元测试或组件测试；
3. 跨模块边界的集成测试；
4. 相关用户流程或业务流程测试；
5. 与变更影响相匹配的回归测试。

检查失败时，诊断失败原因，区分产品缺陷、环境问题和已有失败；修复范围内缺陷后，重新执行失败检查及受影响的回归测试。必需检查仍失败时，不得将当前步骤标记为完成。

存在适用的测试 skill 时调用它。保留具体证据，包括执行命令、结果和限制。对于界面或文档输出，只要布局或交互会影响结果，就执行可视化检查。

## 最终验收门禁

完成任务前：

- 将每个需求编号与实现内容和测试证据逐一核对；
- 执行组合流程测试及适当范围的回归测试；
- 检查差异，排除意外修改、兼容风险、敏感信息、调试内容及缺失文档；
- 在适用时确认迁移、生成文件、部署和回滚说明；
- 汇报已交付行为、关键修改文件、验证结果、假设及剩余风险或阻塞项。

准确标明最终状态：

- **完成：** 所有必需验收标准均已实现并验证。
- **部分完成：** 已完成有效的范围内工作，但仍有明确列出的验收标准未完成。
- **阻塞：** 继续推进需要用户决策、新权限、不可用依赖或外部状态变化。

对于多模块用户流程，不得仅凭单元测试通过就判定整体工作完成。
