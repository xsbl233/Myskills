# humanize-check —— 人性化 · 易读 独立复检门禁

**定位**:胶片 / 文档 / 网页 / 月刊周报定稿前的**独立复检**(视角独立于作者),专挑「读起来别扭 / 不像人话 / 只说一半 / 模棱两可」的点。

它是**通用收尾门禁**——任何「最终产物是给人读的文字」的 skill 都可以在收尾时起一个独立 subagent 调用它(见「被谁调用」),人性化表达的标准因此只需维护一份。

为什么要独立跑:作者对自己写的句子会「读顺」——那些别扭的措辞在写的时候是有语境的,回头再看仍然读得通。只有换一个不带作者语境的视角,才能发现「这句话别人看不懂」。

## 输入

一个 `.pptx`(或 md / HTML / 纯文本)路径。

pptx 先取正文:`python -m markitdown deck.pptx`,或用 python-pptx 遍历 runs;并**渲染出图**看观感——`soffice --headless --convert-to pdf --outdir <dir> deck.pptx` + `pdftoppm -png -r 150 <dir>/deck.pdf <dir>/slide`(Linux 上 `soffice` 一般在 PATH;macOS 在 `/Applications/LibreOffice.app/Contents/MacOS/`)。

**只读源码不出图,查不出观感问题**——字号、对齐、密度、断行都得看渲染结果。

## 复检清单(逐条过,给 before→after)

### 1. 像人话 / 易读

无生硬、负面、技术黑话 / 内部黑话——如「暴露」「hack」「侵入式」「上抬(至平台)」「赋能」「抓手」「颗粒度」「拉齐」「打法」之类。

还有几类**看着像人话、其实很别扭**的,一并换掉:

- **虚指的大词**:「公开世界能告诉我们什么」→「真实实测数据」/「公开数据里有什么」;「业界」「生态」当主语。
- **口语化的疑问式标题**:「一口气干多久」「能干多久」→ 直接用**名词化的正式说法**(「长任务表现」);标题不是弹幕。
- **「好消息 / 坏消息」这类框架词**:后面跟的内容往往并不真对应好坏,读者反而要猜。**不明显是好是坏的,直接平铺陈述**;真要强调再用「值得注意的是」。同类还有「遗憾的是」「令人惊讶的是」「有趣的是」。
- **黑话直译**:根因 / 上游合入 / 落地 / 降本 / 打底 / 横比 / 天龄 / 墙内 / 价值点 → 原因 / 主干合入 / 部署 / 压低成本 / 先顶上 / 拿来对比 / 只有 N 天 / 境内 / 地方。
- **动词与宾语要搭配**:写出来的动宾短语读一遍,动作和对象对不上就换动词——「把分数**打折听**」→「打折**看**」(分数是看的不是听的);同类如「聆听数据」「触达结论」。
- **生造的「XX 税」「XX 债」类套壳比喻**:「速度税」「幻觉税」这种机械套格式的比喻,一律拆开直说问题本身——「代价是输出速度明显偏慢」「但错误断言率最高」。比喻只有真帮助理解时才留(且要解释);套格式的不留。

**优先自然说法**(如「上抬至平台 GCC 15」→「**迁移至 / 升级到 GCC 15**」)。标签让**非专业读者一眼看懂**。生硬词遇到就替换,并把新发现的黑话补进本清单。

| (标题)三个综合榜互相打架,又各有王者 | 三个综合榜略有差异,但在我们关心的维度趋势明显 | **标题位从严**:打架 / 王者式口语比喻正文尚可斟酌,标题一律改为平实的结论陈述 |

几条**通用规则**从上表抽出,单独记住:
- **「X 不是 A,是 B」式对仗警句**和**把长概念压成两三个字的残缺短语**(「切到维度」「权重像你的场景」),一律展开为完整的主谓宾直说。
- **文字改动会连累截图**:正文里重命名(如轴→维)、改标题后,渲染截图里还是旧词——检查产物内嵌图片的文字与正文是否同步,不同步就重截。
- **对照表按词根执行,不只匹配原句**:「的一侧」清了,「Anthropic 侧」「两侧」也要清;「排序翻了没有」改了,「排序可能翻」也要跟着改。复查时对每个表项搜词根。
- **括号注释必须紧跟被解释对象**:挂错位置会张冠李戴(把解释「不硬编率」的括号挂在「价格竞争力」后面,读者会以为在说价格)。
- **定性断言要跨全文交叉核对**:「全场最高」「唯一」「第一」这类归属,和文中其他章节说法对一遍,常见错法是换个章节归属就变了。
- **专有名词与编号首现要可定位**:裸编号(1035)写全(GCC14-1035);全篇只出现一次的专有名词(某个榜单名、某个产品代号)首现必须给一句「是什么」。
- **md 镜像不得残留 HTML 交互说明**:「悬浮可见」「点『表』」在 md 里是死指令,改成「见 HTML 版(悬浮 / 点表查看)」。

### 2. 完整不半句

关键点没有「只说一半」——比如说「开源」只提了插件却漏了补丁、或漏了固件闭源;依赖 / 风险只列一半。

### 3. 结论有明确观点

明确推荐哪个 + 讲清**为何不选其他**,不笼统模棱两可;推荐项在版面上有标注。

### 4. 标点跟随文种(铁律)

中文语境的 `, ; : ( )` **一律全角**(，；：（）),**严禁半全混用**。

机械规则:标点的前一个或后一个渲染字符是汉字(含中文标点)就转全角;括号看内容是否含汉字、或前邻是否汉字。

**例外**:千分位 / 时间 / 比例(`1,632`、`3:1`)等数字两侧的 `,` 与 `:`、纯 ASCII 内容且不邻汉字的括号、代码 / 文件名 / URL。

**机械规则抓不到的一类要人工扫**:标点前后都是拉丁字母或数字、但语义上是中文句内停顿的——「给 Opus 5,LiveBench 给……」这里两个英文名之间的停顿仍属中文语气,要全角。判据:把英文 token 当成中文句子的成分来读,这个停顿如果属于中文句子,就用全角。

pptx 可用同仓 `pptx-pro` 的脚本批量修:`python ../pptx-pro/references/punct-normalize.py deck.pptx`(先加 `--dry-run` 看)。**有构建脚本的文档,把规则放进构建管道的源头统一处理,不要每次手修。**

注意转换次序:括号全角化之后要**再跑一遍**逗号 / 冒号 / 分号通道,否则会残留「）;」这类半全混排。

### 5. 前后表达一致(重点)

通篇扫**同一概念的不同写法并统一**——大小写(`BASE` vs `base pattern`)、中英混写、简写 vs 全写(`GCC12` vs `GCC 15`)、产品名的不同叫法、内部数字代号。同义反复、前后口径矛盾一并揪出;内部代号首次出现要澄清或注明。**同一概念只用一种写法。**

### 6. 无 AI 腔 / 口水

去套话、去冗余修饰。若项目里有写作风格约定(风格指南、语气卡片),一并对照。

### 7. 每节结论先行(重点)

每个章节 / 每页的**开头几句必须直接给出这一节的结论**,而不是「这一节讲什么」的目录式导语,更不能一上来就摊数据表。

判据:只读开头两句,读者能不能复述出这节的结论?不能就改。推荐写法:「**先说结论:……**」+ 一到两句支撑。

### 8. 目录 / 大纲与标题一一对应

侧栏、目录、页眉里的短标题,必须是正文标题的**前缀或明确对应**(「稳定性实测」←→「稳定性实测:同一道题重跑一遍,结果差多少」)。出现短标题与正文标题对不上的,一律改。

### 9. 观感

字号 / 配色 / 对齐是否让阅读顺畅(与 `pptx-pro` 的版式红线呼应)。

### 10. 缩写 / 英文专名首现给括号解释

较专业或不通用的缩写 / 英文名,**首次出现**时加中文全称(如 `SBOM(软件物料清单)`、`BCI(基础容器镜像)`、`OBS(开源构建服务)`、`IMA(完整性度量)`)。

**但目标读者都懂的基础 / 场景常识术语不用解释**(如 GCC、SUSE、GPL、SELinux、glibc 等),免得啰嗦——判据:**该读者群是否需要这层解释**。

## 如果产物是 HTML / 网页,额外查这四条

中文排版在网页上有几个**只在浏览器里才看得见**的坑,静态读源码发现不了——必须渲染出图核对:

1. **源码换行会变成可见空格**:HTML 里两个汉字之间的换行,渲染时折成一个空格(`404。 这份报告` 中间会多一个空)。做法:跨行内标签判断空白两侧字符,两边都是中日韩字符就删掉空白,一边是拉丁文才保留一个空格。
2. **`ch` 不能用来限制中文栏宽**:`ch` 是「数字 0 的宽度」,`max-width: 68ch` 对英文是 68 字,对中文只有约 34 字——会比同页的图表窄一半以上,看着像没写完。中文用 `em` 或干脆不设上限,与同页其他内容共用一列宽。
3. **中文标题会从词中间断行**:中文没有词间空格,`text-wrap: balance` 可能把「什么」劈成两行。把分句包进 `display: inline-block` 的 span,浏览器就会优先在分句之间断。
4. **渲染后再看一遍**:`--headless --screenshot` 至少截首屏 + 一节正文 + 一张图表,宽窄各一次。标签压线、数值重叠、栏宽不齐,只有出图才看得出来。

## 产出与调整(自主为主 —— 默认自己定夺并修改)

- **默认就地改 + 重渲染核对**:措辞更像人话、补全半句、标点归一、术语统一、可读性 / 一致性,以及**能一眼判断的口径顺化**(如「平台锚定 15 却推荐 12」这类自洽补句)——都**直接改**;改完**必出图逐帧目检**,若引起换行 / 溢出 / 错位就顺手收字或调宽再验,直到干净(小改不新起版本)。
- **仅这些情况只报不改**:会变更**事实数字 / 业务取舍 / 你无法核实的口径**,或明显该由需求方拍板的——列成 `建议(未改)` 交用户定夺。
- **数字红线**:凡是经过核验的报告,**一个数字都不许改**。改完自查一遍:把改动前后的全部数值抽成多重集比对,差集应当为空(新增解释性文字带进来的数字除外)。这是最容易犯、后果最重的错。
- **结尾结论**:通过 / **已改 N 处** / 待人定夺 M 条,逐条给 `[类别] 位置 —— 现状 → 已改成 / 建议`。

## 两阶段复检流程(固定动作,每次都走)

1. **机械阶段(主 agent 自查)**:按上面的清单 + 对照表逐条过。能脚本化的先脚本化——标点全角检查、对照表词根搜索、数字多重集红线。
2. **独立挑刺阶段(必做,不是可选项)**:**另起一个独立 agent**(不共享作者上下文、不复用作者措辞偏好、挑刺心态),对全文自由复检,专找机械规则抓不到的:表达不合理、不清晰、不通顺、不人性化、不易读、不易理解、前后矛盾、首现无解释。产出**分级报告**——`必改 / 建议改 / 可留(带理由) / 对照表残留复查 / 统计`,每条带原文摘录以便定位。报告先交用户过目;用户拍板后由主 agent **逐条确认再修改**——每条先核事实(报告本身也会误判,比如把正确的「全场最高」当成矛盾),判定不改的写明理由,处理结果回附到报告末尾归档。
3. **回写迭代(闭环)**:本轮确认的新坏表达 → 进对照表;新类型的问题 → 进复检清单;新踩到的流程坑 → 进对应小节。**skill 本身每轮自我更新**,让下一轮的机械阶段能拦住这一轮的漏网——这是本 skill 的核心机制。

## 独立性(关键)

挑刺阶段的 agent 必须**独立运行**——**不复用作者的思路与措辞偏好**,默认「挑刺」心态,宁可多报可疑点(可留项交由主 agent 或用户裁决)。这样才能抓到作者自己看不见的「读起来不像人话」的盲区。

## 被谁调用(通用收尾门禁)

本 skill 不绑定任何一种产物形态,**任何「最终产物是给人读的文字」的 skill 都可以在收尾时调用它**,用一套统一的标准把住人性化表达这一关:

| 调用方 | 产物 | 在哪一步调 |
|---|---|---|
| `pptx-pro` | 决策胶片 / 汇报页 | 渲染目检通过后、存版本前 |
| 月刊 / 周报 / 简报类 skill | 中文 digest、动态汇总 | 拼完全文、发出前 |
| 博客 / 文稿类 skill | 公众号文章、技术博客 | 定稿前 |
| 设计文档 / 分析报告类 skill | Markdown + docx、评估报告 | 交付前 |

调用方式:用 Agent 工具起一个**独立 subagent** 执行 `humanize-check <产物路径>`——必须独立起,不能在写作者自己的上下文里顺手跑一遍,否则就丢掉了「视角独立于作者」这个核心价值(见上一节)。

也可以手动对任意 md / HTML / pptx 直接调用。

**这样做的好处**:人性化表达的标准只维护一份。上面那张「已纠正表达对照表」、结论先行、术语一致、标点跟随文种这些规则,不需要在每个产物型 skill 里各抄一遍——它们改一次,所有调用方同时受益。
