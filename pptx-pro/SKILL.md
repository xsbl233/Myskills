# pptx-pro —— PPT 制作规范 skill(叠加在官方 `pptx` 之上)

**定位**:官方 `pptx` skill 提供机制,本 skill 叠加**制作规范与硬性红线**(优先级高于官方的「设计自由发挥」)。做 deck 时:先按本 skill 的偏好与红线,底层能力调官方。

本 skill 的红线不是凭空写的设计教条,而是从多轮真实交付的返工中沉淀下来的——每一条背后都有一次「渲染出来才发现不对、推倒重做」的代价。方法论层面的实证归纳见 `references/feedback-patterns.md`,拿不准时回查。

## 一、底层机制 → 直接用官方 `pptx` skill

| 能力 | 做法 |
|---|---|
| 读取 / 提取文本 | `python -m markitdown deck.pptx` |
| 缩略图目检 | 官方 `scripts/thumbnail.py deck.pptx` |
| 从零构建 | 官方 `pptxgenjs.md` |
| 模板编辑 / 解包 / 校验 | 官方 `editing.md`、`scripts/office/*` |

官方 skill 通常安装在 `~/.claude/skills/pptx/`(或所用 Agent 平台的等效 skill 目录)。需要官方用法时去读它的 `SKILL.md`,别在这里重复。若环境里没有官方 pptx skill,底层依赖(pptxgenjs、markitdown)需自行准备,本 skill 的规范部分仍然适用。

## 二、默认偏好(没有特别要求就这么做)

- **配色**:深灰 charcoal(`2B3A42`)底 / 头 + 单一强调色(默认墨绿 `3C7D5E`);发丝边框(`E2E6E8`);正文灰阶(`27333A / 515D64 / 8B959B`)。克制不花,**全篇只用一个强调色**。
- **版式**:卡片式;等宽栏(如 50/50);统一内边距 `PAD ≈ 0.26"`。
- **字体**:CJK 用 `Microsoft YaHei`;字号收敛到 标题 / 正文 / 标签 三个角色;**标点跟随文种——中文用全角标点,不混半角 ASCII(见 §三.8)**。
- **构建**:优先 **pptxgenjs 从零构建**,产出**可复现脚本** `build_*.js`,内置几何 + `[OUTSIDE-CARD]` 审计。起步直接复制 `references/deck-scaffold.js`(含 palette / card / cardTitle / sectionTag / audit)。
- **渲染核对(必做)**:`soffice --headless --convert-to pdf --outdir <dir> deck.pptx` + `pdftoppm -png -r 150 <dir>/deck.pdf <dir>/slide`。Linux 上 `soffice` 一般已在 PATH;macOS 在 `/Applications/LibreOffice.app/Contents/MacOS/`(需加 PATH),`pdftoppm` 来自 poppler。**容器里渲不出图就到有图形栈的机器上出图**,不许跳过这一步。
- **归档**:产物与构建脚本同目录同次提交;**版本策略权衡**——大改留新版本(v2 / v3…),小改就地改(见 §四.3)。

## 三、版式红线(渲染核对,不得再犯)

1. **对齐一致**:同列 / 同卡的标题与正文统一左内边距;禁「标题在左 + 正文顶右」与「标题在上 + 正文在下」混排;label+value 用固定 label 列宽,让 value 对齐成列。
2. **卡内留白**:文字四周留 padding(顶 ~0.13 / 底 ~0.14 / 左右 ~0.26"),不得贴边或超出卡框,尤其是底部标签行。
3. **图标 / 序号圆与文字 ≥0.2" 间距**,禁贴字压字。
4. **内容上移 + 单行垂直居中**;多行块顶部留白,别压到卡底。
5. **渲染核对不可省**:pptxgenjs 几何审计查不出「文字出框 / 贴边 / 换行溢出」,必须出图目检;脚本里加 `[OUTSIDE-CARD]` 审计(每段正文 bbox 须落在某张卡框内)。
6. **字体 / 字号统一**到少数角色;配色克制(见上)。
7. **同源信息相邻聚拢**(如某平台与它的约束条件),不被其他主题的卡片打散。
8. **标点跟随文种**:中文正文用**全角中文标点**(,。:;、!?()《》「」""''……——),**不要在中文里混用半角 ASCII 标点**(`, . : ; ( )` 等)——字是 CJK、标点却是字母类型的,看着很怪。纯拉丁 / 数字 / 代码 / 版本号段用半角;中英混排时标点归属看**紧贴的那侧文种**(`/ - . · ——` 等分隔符不动)。**既有 / 手改的 deck 也要跑核对**:用 `references/punct-normalize.py deck.pptx`(先 `--dry-run` 看)批量转——只改 `<a:t>` 正文、括号成对判中文、逗号 / 分号 / 冒号看相邻中文,自动保护标签 / 代码 / 文件名 / 实体。
9. **内容密度红线(每页渲染后自问「这页空不空」)**:出图目检不只查出框,还要查**空洞与留白失衡**——半页留白 / 一张卡只有一行字 / 栏间密度悬殊,都算不合格。空洞页只有两条路:**用真实素材有效补充**,或**开口向用户要材料**;禁止交付空架子。
10. **素材主动性 + 拿不准必须问**:用户要「形象化 / 图案 / 类比」时**主动取材**——可上网下载官方 logo / 示意图(注明来源并自行核实授权),可原生绘制图形(图标 / 星芒 / 链条),可把 md / 数据渲成「文档截图」(HTML → soffice → pdftoppm → PIL 裁剪)。用户点名的素材(会话片段 / 截图 / 目录)找不到或含义不明时,**先问清再动手,绝不按猜测替代**——猜错一轮浪费的时间远大于问一句。
11. **贴图只缩放不变形**:嵌截图 / 照片一律 contain(保持原比例),禁止 cover 裁切拉伸导致内容变形;截图内文字应至少「标题可读」,糊到不可读的图要么放大要么裁局部。

## 四、内容 · 结论 · 版本红线

1. **不盲从原始材料**:主动挑出口语化 / 术语不规范 / 含义不清的表述(内部代号、「hack」之类),改为正式官方表述;含义拿不准**先问用户**,不照抄。
2. **建议 / 结论必须有明确观点**:明确推荐哪个方案 + 讲清**为何不选其他**,禁笼统模棱两可;先全面权衡给出倾向,**确实不确定再与用户对齐「目的 / 意思」**;推荐项在版面上显式标注(`★ 推荐` 徽章 + 卡片高亮描边)。
3. **版本策略(权衡,别一刀切)**:**有意义的结构 / 内容改动,或需要保留对比基线** → 出新版本文件(v2 / v3…);**细小修补(错别字 / 单个措辞 / 小位移)** → 直接在**当前版本上改**,不必新起版本。默认:大改留版本,小改就地改;拿不准偏向就地改,并在提交信息里说清。
4. **人性化 · 易读**:用词优先**人性化、易读**,避免生硬 / 负面 / 黑话——如「暴露」→「开放程度」、「hack」→「侵入式实现」、「冲榜」→「面向基准调优」。标签与结论要让**非专业读者也能一眼看懂**,读起来不冷、不隔。

## 五、细节基准(多轮真实交付实证;详见 `references/feedback-patterns.md`)

1. **量化数据一律正值表提升**:耗时下降换算成 加速倍数 / +%(如 -91.2% 耗时 → 11.4×;-41% → +69%),**原口径保留在小字括注**;严禁同页正负混排。全篇量化数字统一用**主强调色**;分类标签 / 状态色(证伪、警示)不算数字,各归各色。数据大卡(hero)**居中对齐**。
2. **忠实呈现用户点名的内容**:用户给定的标题 / 名称 / 引文**一字不差照抄**(可精简,不可转述改写风格)。引用一段自然语言指令上片,就要**看起来像那段指令**,禁止擅自改写成伪代码或摘要体;需要表达排版对应关系时,用缩进 + 行注(↔)而不是改写原文。
3. **事实引用前先核最新状态**:PR / 仓库 / 特性状态每次上片前**拉一次最新数据**(state、merged_at、描述要点),不许沿用旧稿口径——「WIP」写成已合入、或反过来,都是硬伤。表述用**具体仓库名**,不含糊说「合入上游」。
4. **归属措辞精确**:同一个人在不同社区 / 组织的产出,归属不能混写——文章属于哪个社区、代码或 skill 属于哪个项目,标题与页内标注都要分清,拿不准先问。
5. **常见生硬表述替换**(中文写作,直接执行):契约→规范;深潜→深入;呼应→结语;「锁到」→「锁定到」;「抬到 / 上抬」禁用,改「迁移到 / 升级到」;「守正确」→「把关正确性 / 守住正确性」;「变贱」→「变廉价」;「不信散文」→「不认自然语言描述」。
6. **同列左对齐是最常见的返工点**:同一栏内的引句 / 正文 / 量化条 / 卡片**严格同一 x 左缘**(用同一个 midX 变量,别各写各的);首行文字与相邻图片列间距 ≥0.4"。改对齐这类反馈,修完必须**放大渲染图逐像素核对**——±0.1" 的微调肉眼看不见,等于没改。
7. **图大于文**:证据截图尽量大、铺满栏宽,文字压缩上移让位;「背景 / 劣势」类顶卡要矮、文字垂直居中,版面重心留给下方的成果与图;三联图**比例一致**(需要裁剪的先渲出来给用户看,用户可能要求用原始图)。
8. **品牌 / 形象素材**:涉及某产品的形象素材,**先查用户已有的主题配置与官方素材源**,按其配色重着色;自绘的替代物基本都会被否——「我之前调过颜色」这类话是最强的定位线索。素材来源与授权自行核实,不确定就换自绘或问用户。
9. **图形工程**:pptxgenjs 的 `sizing: contain` 经 LibreOffice 渲染会拉伸变形——一律按**实测宽高比手工居中**(维护一张 ASPECT 表);流程分叉用**竖干 + 水平箭头**正交连线,禁斜线;mini 装饰图与卡框留 ≥0.12"。
10. **参照物先打开再动手**:用户指到的具体文件 / 页码 / 卡片(某胶片第 N 页、某知识卡、大纲第 N 行、某次会话),必须先渲染 / 读原文再设计,禁凭印象。

## 六、快速起步

1. 从零做 deck → 复制 `references/deck-scaffold.js` 起步,按上面的红线填内容。
2. 每改一版 → `AUDIT=1 OUT=<路径> node build_*.js` 过审计 → `soffice` + `pdftoppm` 出图**目检**。
3. **收尾门禁(定稿前必做)**:用 Agent 工具起一个**独立 subagent** 跑 `humanize-check <deck.pptx>` —— 做「人性化 · 易读」独立复检与调整(视角独立于作者,专挑不像人话 / 只说一半 / 模棱两可)。过检后再存版本 / 交付。
4. 需要官方底层用法 → 读官方 `pptx` skill 的 `SKILL.md`。

## 七、故障排除

| 现象 | 原因 | 解决 |
|---|---|---|
| 渲染出的图片被拉扁 / 拉长 | pptxgenjs `sizing: contain` 经 LibreOffice 渲染不生效 | 实测原图宽高比,手工算 w/h 并居中,别依赖 `sizing` |
| 几何审计通过但文字仍溢出卡框 | 富文本多 run 各自 fontSize 时,审计用外层字号估宽会误报 | 顶层补一个近似 fontSize;并以渲染出图为准 |
| 大标题改字后换行位置变了 | 含全角标点时字宽估算与半角不同 | 改完大标题必须重渲一次复核换行 |
| 状态符号渲成乱码 / 字形错乱 | LibreOffice 对部分 emoji 缺字形 | 状态符收敛到 ✅ ❌ ➖ ⚠️ 这几个 |
| 抠出来的图边缘有锯齿 | JPEG 抽帧有 1–2px 底噪 | 按逻辑像素网格投票重建;PIL bbox 裁剪改用阈值化或固定裁 |
| 容器里 `soffice` 跑不出 PDF | 容器缺图形栈 / 字体 | 到有图形栈的机器上渲,不要跳过目检 |
