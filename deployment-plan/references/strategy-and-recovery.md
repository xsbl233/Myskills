# 发布策略与恢复判断

## 按现有能力选择

| 策略 | 适用前提 | 必须写入计划的限制 |
| --- | --- | --- |
| 停机替换 | 可接受明确停机窗口，适用于资源受限或不兼容升级 | 维护模式、停写/排空、备份、最长中断时间、启动失败的恢复路径 |
| 滚动发布 | 多副本、健康探针、新旧版本可并存 | 最大不可用容量、连接排空、混合版本兼容、停止滚动条件 |
| 蓝绿发布 | 能维持两套环境并切换入口 | 额外容量、共享数据兼容、长连接与后台任务归属、切回后的数据状态 |
| 灰度发布 | 可隔离用户/流量或实例，且有分组观测能力 | 分组方式、对照基线、代表性、最低样本量、放量与停止条件 |

若用户要求的策略缺少必要能力，写明差距并提出最小可行替代，不虚构平台能力。单副本滚动更新、DNS 切换和共享数据库的蓝绿发布都不能自然保证零停机或立即恢复。

## 有状态变更

涉及 schema、数据格式、API/事件契约或缓存序列化时才应用本节：

1. 明确所有生产者、消费者与旧版本共存周期；检查旧代码对新数据的读写能力。
2. 优先评估 expand → migrate → contract：先添加兼容结构，再切换代码或回填，确认旧消费者退出后另行删除旧结构。双写不是默认要求；采用时必须处理部分失败和一致性。
3. 大表变更评估锁、耗时、复制延迟与容量；回填描述分批、断点、幂等、进度核对及中断后的继续方式。
4. 破坏性变更前写明备份范围、恢复演练证据、停写或写入围栏以及恢复后的数据核对。恢复旧备份可能丢失备份后的合法写入，必须说明这部分写入如何保存、重放或由业务接受损失。
5. 标明回退应用仍安全的最后节点。跨过该节点后，选择经论证的前向修复、兼容补丁或数据恢复；不要给出通用 down migration 作为万能回滚。

## 常被漏掉的边界

- 队列与定时任务：灰度和蓝绿可能同时消费或重复调度，需说明任务所有权、排空与幂等。
- GitOps：恢复应更新实际声明源；只手改集群可能被控制器覆盖。
- 配置与功能开关：记录与制品版本的配套关系、默认值及关闭开关的效果。
- 静态资源/CDN：考虑 HTML 与资源版本共存、缓存失效及旧资源保留期。
- 外部不可逆副作用：通知、支付、第三方写入需要补偿或对账，回滚代码不能撤销它们。
- 多区域：逐区域推进，确认共享依赖和跨区数据兼容，不把一个区域成功等同于全局成功。

## 放量门禁

对每个阶段记录：当前范围 → 目标范围、最长观察时间、最低样本数、业务和技术指标、数据来源、基线、继续条件及失败动作。流量低时应延长观察、采用已授权的合成验证或停止放量，不以零错误样本认定成功。

阈值优先采用既有 SLO、告警与历史基线。必须新设时给出推荐依据并标为待确认，避免固定复制“5% → 20% → 100%，各等五分钟”。
