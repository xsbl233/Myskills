# 测试环境与执行计划编写规则

编写每份部署计划的七个测试小节时读取。复用项目现有工具；具体命令来自仓库脚本、锁定版本或官方文档，不凭技术栈名称猜测入口。计划中的命令默认为待执行。

## 1. 如何启动测试环境

写明执行主机、shell、工作目录、环境标识、运行时/依赖版本、资源与端口、凭据注入方式以及启动前检查。给出按依赖顺序的具体命令：准备依赖 → 启动基础服务 → 适用的迁移/初始化 → 启动应用 → 就绪检查。

优先复用 Compose、项目启动脚本、CI 环境或已有部署工具；不强行引入容器。区分首次启动和复用已有环境，说明已有数据处理、重复执行是否幂等、后台运行方式、日志位置、停止与清理命令。清理仅限本次创建且明确归属的资源，不默认删卷或重置共享数据库。

说明与生产的差异及其影响；明确外部依赖采用真实测试服务、沙箱或 mock。支付、短信、邮件、队列和定时任务需确认测试目标及隔离方式，避免测试误触生产行为。

## 2. 使用什么数据集

按测试目标选择最小但有代表性的数据，不默认下载大型公共数据集。优先检查仓库 fixtures、seed、golden files 和团队已维护的基准数据。

为每个数据集记录：ID、用途及覆盖用例、来源、不可变版本或生成器提交、格式/schema、条数与体积、必要的分布/边界、预期输出或断言基准。按需区分冒烟、回归、性能数据；性能集必须说明规模、访问分布和并发假设，不能用几条冒烟数据证明容量。

合成数据固定随机种子、生成器版本和参数；静态站点可用路由清单、资源列表和预期页面内容。模型类项目按需区分训练/验证/测试集并避免泄漏。真实业务数据需有已授权来源和脱敏规则，不默认复制生产库。

## 3. 数据集如何获取

给出具体获取位置（仓库路径、对象存储 URI、下载链接或生成脚本）、访问权限、获取命令、下载/缓存目录、解压/导入目录及磁盘空间要求。记录许可证或使用限制（适用时）。

固定对象版本或校验摘要，并说明如何验证完整性、schema、行数与关键字段；没有已知摘要时不编造摘要，明确来源缺口。记录初始化/导入命令、导入后验证、重跑去重或重置策略以及无网/权限不足时的替代方案。替代数据覆盖不足需明确，不能静默当成原数据集。

## 4. 测试结果保存目录

优先沿用项目报告配置。没有约定时建议 `<project-root>/artifacts/test-runs/<run-id>/`，在实际计划中解析为目标机器的绝对路径；`run-id` 包含带时区时间戳、提交短标识和唯一后缀，重跑不得覆盖原始结果。

按实际测试工具选择文件，不强迫产生无用报告：

| 内容 | 建议位置 | 用途 |
| --- | --- | --- |
| 执行元数据 | `run-manifest.json` | 记录源码/制品版本、环境、数据集版本或摘要、工具版本、命令（脱敏）、开始/结束时间、退出码及重试关系 |
| 摘要与机器报告 | `summary.md`、`junit.xml` 或工具原生 JSON/HTML | 区分通过、失败、阻塞、未执行、跳过；汇总实际执行数 |
| 环境与测试日志 | `logs/` | 保留启动、就绪失败和测试输出 |
| 失败证据与指标 | `evidence/`、`metrics/` | 按需保留截图、trace、性能指标与对照结果 |

写明创建目录的方法、写权限、容器路径到宿主机的映射、CI artifact 名称及上传位置、访问权限和保留期。失败/超时也要归档；报告中不保留凭据和未脱敏业务数据。报告文件的实际路径必须与命令参数一致。

## 5. 如何判断测试环境可以使用

建立逐项就绪表，每项有检查命令、预期输出、超时、轮询间隔及失败处理。按系统实际检查：

- 资源与配置到位、目标制品/配置版本正确。
- 进程/容器存活；端口可连仅作为基础检查。
- 应用就绪接口返回约定状态及必要内容；不能只检查 HTTP 200 或固定睡眠若干秒。
- 数据库/缓存/队列等依赖可访问、迁移版本正确。
- 数据已导入且数量/关键约束正确；测试账户与权限可用。
- 一条代表性业务冒烟可完成，必要写操作使用隔离数据并说明清理方式。

静态站点等无状态项目按其实际依赖裁剪检查。所有必需项通过才允许正式测试；失败时停止后续测试，保存诊断信息并标记“环境阻塞”。分别记录“环境可测试”和“本次测试通过”，前者不证明后者。

## 6. 如何启动测试

给出每类测试的用例范围、前置依赖、shell/工作目录、环境绑定、数据集、完整入口命令、并发/种子、报告路径、超时、通过标准和失败处理。通常先就绪检查，再冒烟，再按依赖运行回归/集成/E2E，性能或稳定性测试按项目需求加入。

优先引用已有脚本。入口缺失且确有必要时，生成与项目工具匹配的最小脚本，并在计划中链接该脚本。脚本必须：

- 在启动前检查必需参数与目标环境，缺失参数明确报错，不隐式指向生产。
- 有有限等待和超时；失败返回非零退出码，不用日志管道吞掉测试失败。
- 在成功、失败或超时后尽力保存日志、报告与状态，并只清理自己创建的资源。
- 说明依赖安装、调用示例、输入输出、预期退出码和是否实际验证；不能提供永远成功的占位脚本。

“退出码为 0”只是条件之一。要求必需用例确实执行、断言满足、报告存在且可解析；零用例、全部跳过或缺失报告不能视为通过。记录允许跳过/已知失败的具体范围与依据；重试保留第一次失败，偶发失败单独标记，不隐藏不稳定性。

## 7. 预计测试耗时

按阶段列出环境准备、镜像/依赖拉取、数据下载/生成、导入、就绪等待、各类测试、报告归档与清理的时间区间；区分纯测试执行时间与端到端总耗时。注明硬件、数据量、并发、缓存冷热状态、网络和估算证据。

优先使用同等条件下的 CI/历史运行；只有吞吐量时用 `数据量 / 有效吞吐量` 估算并列出假设。并行阶段按依赖图的关键路径估算，不把所有耗时相加，也不简单除以线程数。计划中的超时上限与预计耗时分开。

无历史数据时写“粗估、低置信度”，提供有依据的区间；连规模都未知则写“待测”，列出一次小规模校准运行的命令/样本量与外推方法，但不擅自执行。设置重试预算和缓冲并解释依据，不给伪精确的承诺。
