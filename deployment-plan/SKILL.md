# 部署计划生成

将项目证据转化为执行人员能按步骤操作、按指标判断、遇到失败能停止或恢复的部署计划。默认使用中文，遵循用户指定的语言、平台、篇幅和文档格式。

## 必备交付内容

每份部署方案都必须包含以下五个部署章节及下述七个测试小节，简版也不能省略。资料不足时保留章节并说明待确认信息及其影响，不编造内容；不适用的具体字段说明原因。

1. **部署环境**：目标环境、操作系统及架构、主机或云资源、运行时与依赖版本、资源要求、网络端口、访问权限和必要配置；区分现有条件与待准备条件。
2. **源码获取方式**：仓库或源码包地址、获取方式及命令、所需权限和认证方式（不含密钥）、分支/标签及精确提交、检出目录；按需说明子模块、Git LFS 与完整性校验。若由 CI 构建并仅向目标环境交付制品，说明源码由谁在哪里获取、制品地址及其与源码版本的对应关系，不要求生产主机拉取源码。
3. **部署路径**：明确源码/构建目录、程序或制品目录、配置、日志、持久化数据及备份路径，注明所属主机或容器、目录权限与持久化方式。采用容器时区分宿主机与容器内路径及卷映射；托管平台无固定主机路径时列出实际部署目标、资源标识和存储位置，不虚构目录。
4. **部署流程**：按依赖顺序提供环境准备、获取源码或制品、构建、配置、数据变更（适用时）、安装/发布、启动或切流的操作，注明执行位置、命令、预期结果与失败处理。与流水线已有步骤对应，避免重复执行。
5. **部署完成后的检测方式**：提供可操作的检测命令、URL 或平台检查入口，以及预期输出、通过标准、超时和失败处理。按实际系统覆盖进程/容器状态、端口、健康接口、关键业务冒烟、依赖连接、日志及部署版本核对；不能仅写“访问正常”。

回滚、风险、放量和评审信息作为补充内容保留，不代替上述五项。

另设 **测试环境与测试执行计划**，包含七个明确小节：如何启动测试环境、使用什么数据集、数据集如何获取、测试结果保存目录、如何判断测试环境可以使用、如何启动测试、预计测试耗时。编写这些小节时读取 [references/test-planning.md](references/test-planning.md)，使用模板中的对应表格。即使没有业务数据库，也要说明测试输入、夹具或合成请求，不能把数据集一栏直接留空。

## 工作边界

- 本技能负责读取资料、分析与生成计划；用户只要求计划时，不发布、不切流、不执行迁移、不修改基础设施或应用配置，也不启动服务、下载数据集、运行负载测试。必要时可以生成项目适用的测试脚本并注明待执行。
- 可以在计划中提供操作命令，但标明“待执行”，区分已核验命令和示意命令。不要为验证命令而触发发布流水线；不要假定名为 plan、validate 或 dry-run 的命令无副作用，先检查其行为。
- 复用已有部署工具和发布流程，不因本技能引入新云厂商、Kubernetes 或额外审批制度。已有授权不重复询问；计划中的业务审批只记录项目确有的要求。
- 缺少环境资料时先完成能确定的部分。未知项标为“待确认”，合理推断标为“假设”，候选阈值标为“建议值”；不能把它们写成事实或已通过验证。

## 1. 建立部署上下文

先读取项目内适用的说明、部署文档、构建清单、容器配置、IaC、CI/CD、数据库迁移与健康检查代码。优先定向搜索，不读取或输出密钥值；仅记录凭据名称、注入方式和所需权限。

提取与本次发布相关的信息，并记录文件路径、版本或用户陈述作为证据：

- 发布范围、当前与目标版本、不可变制品标识、目标环境和账户/区域/命名空间。
- 服务拓扑、上下游依赖、状态存储、队列、定时任务、入口流量及组件发布顺序。
- 构建与部署入口、配置差异、运行时版本、容量和权限前提。
- 源码地址与获取权限、精确版本、源码到制品的对应关系，以及各环境的部署目录、卷映射和存储位置。
- 停机容忍度、发布窗口及时区、可用性目标、监控来源、执行与验收角色。
- 测试入口、夹具/种子数据、数据获取脚本、就绪探针、报告配置、CI 历史耗时及测试环境与生产的差异。

只询问会改变方案的关键缺口，例如目标环境、是否允许停机、数据变更可逆性。不要重复问仓库已有答案。没有仓库访问权限时，明确证据边界并基于用户材料出草案，不虚构扫描结果。

## 2. 选择策略并说明依据

比较与项目相关的选项，选择符合现有能力的方案。静态站点或低风险单机发布可用短计划；生产多服务、数据变更或跨区域发布需要更完整的步骤与失败路径。

需要选择发布策略或涉及数据变更时，读取 [references/strategy-and-recovery.md](references/strategy-and-recovery.md)。至少说明影响范围、可用性限制、新旧版本兼容性、资源开销及恢复边界。不要承诺未经证实的零停机，也不要默认每个系统都支持灰度流量。

把准备、数据兼容变更、应用部署、验证、切流、观察、清理排成依赖序列。仅在依赖和故障隔离允许时标记可并行；不可逆操作应独立列出其前置条件、恢复办法和最晚安全回退点。

## 3. 形成部署 Runbook

以 [assets/deployment-plan-template.md](assets/deployment-plan-template.md) 为起点，保留五个部署章节及七个测试小节，其余内容按实际风险删减或扩展。默认保存到项目的 `docs/deployment-plan.md`；用户指定路径优先，已有发布文档则原位更新或沿用其命名。只有聊天输出能力时直接给完整 Markdown，说明未写入文件。

每个有副作用的步骤写清：步骤编号、前置依赖、目标环境、执行角色、操作或命令、预期结果、检查方法、超时/截止点和失败分支。命令注明工作目录与 shell，明确账户、区域、集群或命名空间的绑定方式；未解析变量不得伪装为可直接运行的命令。

验收应包含可观测条件，而非仅“服务正常”：按项目实际选择错误率、延迟、关键业务交易、资源饱和度、队列积压或数据一致性。为放量条件绑定数据来源、基线/对照、阈值、观察窗口与最低样本量；监控缺失或样本不足时不得自动判为成功。缺乏依据的数值保留为建议，列入待确认项。

回滚覆盖制品、配置、流量以及数据的兼容关系，不能只写“回退版本”。列明触发条件、负责人、恢复步骤、恢复后的验收与超过恢复时限时的处置；有数据恢复需求时注明 RTO/RPO 的目标与依据，不把备份存在等同于可恢复。

## 4. 评审与交付

检查以下真实约束，不为凑齐模板加入不相关步骤：

- 五个必备章节是否齐全且有具体内容或明确缺口？源码版本能否追溯到部署制品，部署命令使用的目录是否与部署路径一致，部署后检测是否给出了操作和通过标准？
- 七个测试小节是否齐全？数据集版本和获取方法是否可复现，结果目录是否对应实际报告参数，环境就绪是否包含依赖与业务检查，测试耗时是否有依据和区间？
- 测试执行是否先通过环境就绪门禁？零用例、全部跳过、报告缺失、超时和失败重试是否会被误记为通过？生成脚本是否保持失败退出码并在失败时归档证据？
- 目标、版本、命令和依赖顺序是否一致，制品是否在验证与发布阶段保持同一身份？
- 每个关键步骤是否有成功判断和明确的停止、重试或恢复分支？重试是否会重复迁移、支付、消息或其他副作用？
- 观察与回退时间是否纳入发布窗口，监控失效时是否有停止条件？
- 旧应用是否能读写变更后的数据；清理旧字段、旧环境与备份是否延迟到兼容窗口结束？
- 未知项是否有影响说明、负责角色及最晚解决节点？文档是否包含敏感值？

状态只使用符合证据的描述：`草案（存在执行阻塞项）` 或 `可供执行评审（文档完整，未执行部署）`。文档评审通过不能表述为生产验证通过。输出文件链接、所选策略、关键执行阻塞项及仍未实际验证的内容；不在完成计划后自动执行上线。

需要回归评估此技能时使用 [references/evaluation-cases.md](references/evaluation-cases.md)。需要了解设计依据或更新实践时读取 [references/sources.md](references/sources.md)，不必在每次规划时加载。
