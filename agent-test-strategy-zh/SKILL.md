# Agent 测试投入策略

英文版：`agent-test-strategy`（内容等价，英文会话用那份）。

## 核心立场

以下三条结论是全部规则的依据（证据见 [references/evidence.zh.md](references/evidence.zh.md)；
当用户质疑成本、或需要你解释预算时再读）。

1. **智能体自写的测试很少改变结果。** 在 SWE-bench Verified 上，六个强模型的已解决与未解决任务，
   写测试的频率相近；用提示词鼓励或压制写测试，解决率变化很小，成本变化很大。
2. **智能体自写的测试是观测手段，不是验证器。** 它们大多只打印中间值，断言是少数派。
   把它当成"可脚本化的调试器"，别当成正确性的门槛。
3. **你自己写的测试，和你共享同一套假设。** 它能证明代码跑起来了，证明不了代码是对的。
   真正的验证来自你没有参与编写的判据（oracle）：已有测试套件、用户给的复现步骤、隐藏测试或黄金测试。

所以：测试是**有价格的反馈通道**，不是交付物。只有当信号值这个 token 时才投入。

## 先判断，再落笔

在创建任何测试产物之前，按顺序走这四步：

1. **有没有现成可用的检查？** 已有测试套件、复现脚本、用户给你的命令——直接跑，不要再造一套平行的测试。
2. **只是需要看某个值？** 写一个用完即弃的**探针**（见下）。一个假设一个探针。
3. **项目是否需要长期回归保护？** 把用例清单提给用户，等确认，不要自作主张提交测试文件。
4. **用户是否明确要求写测试或 TDD？** 用户指令优先——要测试先行就转 `test-driven-development`，要写就按他说的写。

第 1–3 步的默认结果：**零个新增的落库测试文件**。

## 探针规则

探针是可执行的临时检查，不是测试：

- 位置：`.dsh/scratch/` 或系统临时目录。绝不放进 `tests/`、`test_*`、`*.spec.*`、`__tests__/`。
- 形态：打印你需要的值；断言可选且只在本文件内。不要 fixture、不要 mock、不要测试框架的初始化。
- 生命周期：用完删除，或留在版本控制之外。它不能随代码发布。
- 不要为了方便写探针去改已有测试，也不要修改断言。

## 停止条件

- 一个假设一个探针。同一个假设第二次失败，是"停下来报告观察结果"的信号，不是扩大测试面积的信号。
- 多写测试不是提高信心的手段，只是提高 token 消耗。说不出"这个测试会改变哪个决定"，就不要写。
- 预算紧张时，先压制测试编写：证据显示成功率只会小幅下降，成本会大幅下降。

## 红旗——出现就停下来重新想

- 唯一断言是 `assertNotNull(x)` 或 `assertDoesNotThrow(...)`。
- 断言内部调用次数或调用顺序（`verify(...)`），重构必然误报。
- mock 掉被测的业务逻辑，而不是只 mock 外部 I/O。
- 为了让检查通过而注释/弱化断言、加测试专用分支、改变实现语义。这是评测作弊（grader gaming），
  在评测审计里是有记录的；不要默默做。
- 写测试是为了"证明"你本来就相信的修复。

## 当测试就是交付物

- 先要用例清单：行为、边界、失败路径。确认之后再写。
- 一个测试一个行为；断言业务值；只 mock 外部边界。
- 提交前自查：实现错了它会不会红？内部重构了它会不会活？任一为否，就修掉或删掉。

## 交接

- 用户要严格 TDD 或测试先行：`test-driven-development`。
- 评审或修复已有测试套件：`brooks-test`。
- 声称完成之前的验证仍然归 `verification-before-completion`；本 skill 只管"要不要写测试"，不管"有没有证明工作完成"。

## 一个例子

Bug：`parse_duration("90m")` 返回 5400，但实际语义是 90 分钟 = 5400 秒，函数却当成了别的单位（分钟/秒混淆）。

- 错误做法：新建 `tests/test_parse_duration.py` 写五个测试，跑通，报告"测试全部通过"。
  成本付了，判据还是你自己的假设。
- 正确做法：先跑现有套件；若确实没有覆盖，写 `.dsh/scratch/probe_duration.py` 打印
  `parse_duration("90m")` 的实际值与期望值，改完再跑一次，删掉。如果这个修复值得长期保护，
  向用户提两条用例，由他决定是否落库。
