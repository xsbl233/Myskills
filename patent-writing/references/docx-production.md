# 交底书生成与排版（docx）

本卡是 SKILL.md §五 的展开部分：**怎么把 Markdown 变成一份代理师读得下去的 docx**，以及交底书与胶片之间怎么对账。骨架（七节）在 `disclosure-skeleton.md`。

**工具链**：`pandoc` ＋ `--reference-doc`。参考文档归档在 `_shared/disclosure-reference.docx`（1 英寸边距那一份）。`_shared/` 里若还躺着别的参考文档，先按 §5.0 核一遍边距，**同一批只用一份**。参考文档从 `pandoc --print-default-data-file reference.docx` 起步，解包改 `word/styles.xml` 与 `word/document.xml` 的 `sectPr` 再打包。列宽用 `_shared/md_table_colwidth.py` 就地改写 Markdown 分隔行。

> **别走 python-docx 那条路**。项目早期用过 `feature-design-doc/scripts/md_to_docx.py`（python-docx），它丢弃 `|---|` 分隔行、硬用 Word 内建 `Table Grid` 样式 —— 于是下面「列宽按分隔行相对长度分配」这一整套都不成立，列宽由 Word autofit 决定、不可控。两条路只能选一条，**本卡全部按 pandoc 写**。

### 5.0 抬头与版式（评审当面提过的几条，做成一次性的固定件）

- **大标题只留主题，括号里的限定下沉为副题**。 「一种 X 的方法（Y 编码 Z：A、B 与 C）」这种标题在目录、页眉、封面里都会被截断； 拆成两行：`# 一种 X 的方法` ＋ 下一行 `**副题**：Y 编码 Z —— A、B 与 C`。
- **版本与修订信息用表格，不用引用块**。引用块里堆四五行「版本｜对应胶片｜对应代码｜事实依据」 读起来是一坨；拆成两张小表 —— 一张「项｜内容」交代当前版本，一张「版本｜改动」做修订记录。 **每条改动一句话**，写清「改了什么、独权范围动没动」，不要复述过程。
- **页边距必须在参考文档里显式写死**，取常规预设 A4 上下左右各 1 英寸（`1440` twips）。pandoc 默认根本不写 `<w:pgMar>`，Word 与 LibreOffice 各按自己的默认渲染，两边打开不一样宽。 项目早期用过窄边距 `left/right="907"`（0.63 英寸）挤版心给表格，**不要再用**：`md_table_colwidth.py` 把计宽标尺硬编码成 `BUDGET = 86.0`（注释即「A4 减左右各 1 英寸的版心」），配 0.63 英寸边距（版心 7.01 英寸、标尺该是 96）跑，会少给约 14% 的宽度，底线里那些绝对字宽的物理含义全错。 **要改边距就同时改 `BUDGET`**，两个数必须一起动。自查：`unzip -p out.docx word/document.xml | grep -o 'w:pgMar[^/]*'`。
- **中文字体要显式指定**。pandoc 的标题样式用 `w:eastAsiaTheme="majorEastAsia"` 走主题解析， 而默认主题里没有中文字体 —— LibreOffice 会回退到某个装饰体，整份文档的小标题变成花体。 把 `styles.xml` 里所有 `eastAsiaTheme="major/minorEastAsia"` 换成 `w:eastAsia="Microsoft YaHei"`， 并在 `docDefaults` 里补一条。
- **表格要有内外框线，黑色**。pandoc 默认的 `Table` 样式只给表头一条下划线， 正文表格连竖线都没有，密集的对照表会糊成一片。在参考文档的 `Table` 样式里补 `<w:tblBorders>`，`top/left/bottom/right/insideH/insideV` 六向全给 `single, sz=4, color=000000`。
- **图与图注居中**。pandoc 把图放进 `CaptionedFigure`／`Figure` 段落、图注放进 `ImageCaption`，三个样式都要加 `<w:jc w:val="center"/>` —— 只改其中一个会出现图居中、图注贴左。 **`<w:pPr>` 必须插在 `<w:basedOn>` 之后**：`CT_Style` 是有序序列（`name` → `basedOn` → … → `pPr`），塞到 `<w:name>` 前面属 schema 违规，Word 会静默丢掉，于是「改了却没生效」。 自查哪几个样式把 `pPr` 插错了位置：

  ```bash
  unzip -p ref.docx word/styles.xml | grep -o 'w:styleId="[^"]*"><w:pPr>'
  ```

做法：这些都不改 Markdown，一次性做进参考文档，生成时 `pandoc … --reference-doc=../_shared/<参考文档>.docx`。参考文档从 `pandoc --print-default-data-file reference.docx` 起步，解包改 `word/styles.xml` 与 `word/document.xml` 的 `sectPr` 再打包。

**改好的模板要归档进仓库**（本项目在 `patent-filing/_shared/`），不要留在临时目录里 —— 否则下一轮重新生成 docx 时又是一份默认样式，表格问题原样复发，而且没人知道上一版是怎么出来的。**同一批只留一份参考文档**：仓库里同时躺着两份边距、字体口径不同的模板时，两个案子会生成出不一样宽的交底书，而这种差异只有并排出图才看得出来。

### 5.1 胶片每精简一轮，交底书就要补一张「落脚对照表」

评审对胶片的删减是**单向**的：胶片越删越薄，交底书是那些细节唯一的去处。 所以每当胶片出新版本、删掉了技术内容，交底书同版次要在文末列出：

| 胶片 vN 删掉的内容 | 本交底书落脚 |
|---|---|
| 某读数的测法（哪个基准、哪个子项、多少次迭代、是否与后文 A/B 同源） | §3.1 |
| 实现函数名与运行时／编译期开关名 | §2.2 术语表、§4.4 取证方式、§4.5 各实施例 |
| 某条收尾规则、某个下位限定、某特征在权项上属独权还是从属 | §4.5.x、§4.6、§4.7 从属权 N |
| 被裁掉的对比文献 | §3.2.1（x）、§6 文献表 |

并在版本块里写明「**自 vN 起胶片不再是这些细节的可引用出处，一律回本文对应章节取**」。 **做法**：拿删掉的每条内容去交底书里 grep 一遍，缺的当场补，不缺的登记落点 —— 不要凭印象认为「交底书里肯定有」。

### 5.2 参考文档缺 `styleId="Table"` → 表格被拍平

交底书七节里有一多半靠表格承载（合规检查、术语、创新点对照、权项要点、检索、文献）。表格一垮，代理师读到的就是一串无结构的段落。

pandoc 生成的表格一律引用 `<w:tblStyle w:val="Table"/>`。**参考文档的 `styles.xml` 里只有 `TableGrid`／`TableNormal` 而没有 `Table` 时**，Word 与 LibreOffice 都退化成无框线、不受列宽约束的散排 —— **XML 里表格结构是好的，所以只有渲染成 PDF 逐页看才发现**，几何上什么都查不出来。

自查：

```bash
unzip -p out.docx word/styles.xml | grep -o 'w:styleId="Table"'   # 空输出就是中招了
```

没有就在参考文档里补一条（`basedOn=TableNormal` ＋ `tblBorders` 六向 `single/sz=4`，见 §5.0）。

**踩这个坑的确切方式：拿 python-docx 生成的 docx 当 pandoc 的 `--reference-doc`。** python-docx 的模板里只有 `TableGrid`，于是产物的 `document.xml` 引 `Table`、`styles.xml` 里却没有这个样式，两边对不上。拿不准就**先用 pandoc 默认样式跑一版对照** —— 默认 `reference.docx` 里这条是齐的。

### 5.2b 列宽：序号列不许占地方，长内容列不许被压扁

pandoc 按 Markdown 分隔行 `|---|` 的**相对长度**分配列宽，所以这是唯一的控制点， 必须按内容重算 —— 等长的分隔行会把「依据」这种长列压成一行七八个字、行高几十行。 本项目实测：一份交底书因此从 36 页胀到 52 页。

工具：`_shared/md_table_colwidth.py <文件.md> [-v]`，就地改写全部分隔行。算法分三层， **顺序不能乱**：

1. **底线（硬）＝ `max(表头宽+3（封顶 18）, 断不开的最长标识符×1.2+2（封顶版心 30%）)`**。 前半让序号、版本这类列到此为止 —— 它们的表头就那么宽，不该再多占； 后半保证 `je_malloc_usable_size` 这种标识符不被从中间劈开（pitfalls C8）。 **断行点算 `/`、空格、括号，不算下划线**；代码字体比正文宽，所以要乘 1.2。
2. **需求（软）＝ `min(该列最长单元格, 平均宽 × 2.2)`**。用平均值封顶， 免得一两个超长单元格独吞预算。
3. **分配**：先把底线发下去，剩余预算按「需求 − 底线」的比例分， 拿满需求的列退出、把富余还给还吃紧的列。

**两个坑都踩过**：
- 只做水填充（需求小的先拿满、剩下的平分）会**把「中等长」和「超长」两列拉平** —— 「结论」和「依据」的需求都超过均分线，于是各拿 27，等于没改。
- 把标识符宽度放进**需求**而不是**底线**，它就会被按比例稀释 —— 需要 34 的列只分到 15，照样断词。**硬约束必须进底线。**

中文按 2、拉丁按 1 计宽；正文 10.5pt、1 英寸边距时取 **86**（与 `md_table_colwidth.py` 的 `BUDGET` 一致，改边距要同步改它，见 §5.0）。

**「预算」是标尺，不是上限。** pandoc 只看分隔行的**相对长度**，所以总和取 86 还是 110 给出的列宽比例完全一样（本项目两份交底书分别是 86 和 110，都渲染正常）。这个数的真正作用是**给底线里那些绝对字宽（表头宽+3、标识符×1.2+2）一个物理含义** —— 版心一变，同样的「18 个单位」就不再是同样的英寸数，底线就错了。所以它不是「超过就溢出」的红线，而是必须跟版心对齐的单位制。

**列数是有上限的。** 七列以上、且每列都是成段文字的表，调列宽救不回来 （86 个单位分七份，每列只剩 8 个汉字宽）。**拆成逐条的两列块**： 每条一个小标题，下面一张「项｜内容」表。本项目的 §4.6 创新点表就是这么拆的。

### 5.3 胶片改了词，交底书要跟着改 —— 跨产物核对

两份产物的用词各自内部一致还不够，**要横着对一遍**。做法是把两边的关键词各数一遍：

```python
deck = 从 pptx 的 <a:t> 里抽出的全部文字
doc  = 交底书 md
for 词 in ('分配侧/分配端', '释放侧/释放端', '归入/归还', '快路径/热路径', 三个短名…):
    print(词, deck.count(...), doc.count(...))
```

本项目实测：胶片那轮 humanize 把「端」统一成了「侧」，交底书那轮 humanize 却把「侧」统一成了「端」 —— 两份产物各自内部一致，合起来正好相反。**两边的 humanize 是独立跑的，谁也不知道对方定了什么。**

- **冲突时以胶片为准**（评审逐轮盯的是胶片，刚定的词就是他要的词），交底书跟着改。
- **权项段落例外**：改之前先把 `独立权利要求 1` 到 `## 五、` 之间切出来，改完原样拼回， 再数一遍「且／或／至少一项／包括但不限于」与各否定式的出现次数，确认一个没动。
- **中英写法不同不算冲突，但要显式声明**：胶片写「尺寸类」、交底书写 `size-class` （与源码标识符对齐）是合理的分工，**必须在 §2.2 写一句「二者指同一概念」** —— 不写，比对两份文件的人就会以为是两个东西。

### 5.4 拿胶片的每一处修订去交底书查一遍

胶片被复检挑出的问题，**交底书上多半也有，而且往往更严重**：交底书更长、写得更早、改的次数更少。 本项目实测：胶片上一处「一批 128 个对象」，交底书里有四处，且整套访问次数推算都建在这个数上； 胶片上两处短名变体，交底书里是六处加十九处。

所以胶片每过一次复检，**把它的问题清单当作交底书的检查清单再跑一遍** —— `grep` 一遍就知道，成本极低。但**逐条判断，不要机械替换**：同一个词在两份文件里的处境可能不同。 例：skill §七 禁「摘要」（会被读成专利摘要），胶片上那处是孤立出现、必须改； 而交底书 §2.2 早已写明「本文中『摘要』一词凡出现均指该数据结构，与专利文件的『摘要』无关」—— 有释义就不必改，改了反而丢掉一个标准术语。**规则是用来判断的，不是用来套的。**
