# patent-writing —— 专利预评估、交底书与 idea 胶片

**定位**：一件专利要交付两样东西 —— **交底书（docx）** 给代理师／审查员，**idea 胶片（pptx）** 给技术评审与 IP 决策。两者共用同一套事实与同一套口径，任何一处对不上都是硬伤。本 skill 管的就是「怎么让它们对得上、且经得起追问」，以及**动笔之前先判清这件专利该不该写、该分几件**。

## 〇、动笔之前：先判该不该申请、该分几件

**这一节的结论会否决或重排后面全部工作。** 交底书写得再漂亮，也救不回一件本来就不该递交的申请。两道关卡，顺序不能颠倒 —— 先判每一件站不站得住，再判这几件怎么打包。

1. **可专利性预评估 —— 主动去驳倒自己。** 把方案拆成 N 条主张，每条至少过三个视角（能不能找到字面公开它的文献／组合两三篇公开文献能不能推出来／代码里到底实现了没有），任一视角判「驳」就不能当独权承重。最容易漏又最致命的三类在先技术：**本团队自有的已合入提交**、**申请人自身的 Issue 与社区提案**、上游竞品源码与学术文献。如实写「6/6 被驳倒」，不要修饰成 4/6 —— 这张表的价值恰恰在于挡住一次不该发生的递交。
2. **专利联盟要在最前面查。** 若本方已加入 OIN 这类交叉许可联盟，而目标软件落在其 Linux System Definition 覆盖范围内，则本案即便授权，对最值得防的对手（往往正好是联盟核心成员）也无法主张侵权。这条决定「是否值得投入」，优先级等同致命风险，必须由 IP／法务核对最新包清单。
3. **打包：合案不抬创造性。** 创造性是**逐项权利要求**判断的，把几个点装进同一个信封，不给任何一条独权增加一个特征。判断合案与否的正确变量只剩**单一性**与**风险隔离**。单一性看**特定技术特征 ＝ 对现有技术作出贡献的技术特征**；「解决同类问题」「落在同一个软件里」「效果可叠加」都不是单一性依据。
4. **同日递交是零成本动作。** 自我夹击这个风险已被两地法律免费解决（中国：抵触申请只破新颖性、明确不评创造性；美国：AIA §102(b)(2)(C) common-ownership 例外）。别为一个已解决的问题去付合案的代价。

**出口只有三种**：不递交（可考虑防御性公开）／收窄后递交（如实说明范围窄、外部不可观测、易规避）／按 N 案同日递交。

> 判据、单一性矩阵怎么列、主张对抗表怎么写、中美条号速查 —— 全在 `references/prefiling-assessment.md`。**这一节只做导航，动手前必须把那张卡读完。**

## 一、先建事实底座

**这是本 skill 最重要的一条。** 不要一边写一边查 —— 写之前先把 `_shared/FACTS.md` 建起来，它是**唯一口径来源**。

```
<项目>/patent-filing/
  _shared/FACTS.md          ← 唯一口径来源
  _shared/decklib.js        ← 胶片共用组件与几何审计
  case1-<名>/               ← 一案一目录
    build_deck_vN.js  build_svgs*.py  images/  <案名>-disclosure.md  <案名>.docx
```

FACTS.md 必须覆盖十一段（模板见 `references/facts-template.md`），缺一段就会在后面某一轮被打回：

| 段 | 内容 | 为什么必须先定 |
|---|---|---|
| 〇 | 本批范围与各案定义 | 防止跨案共用数据、防止出现「兄弟申请」这类会伤单一性的表述 |
| 一 | **PR／代码状态（API 实查，写明核实时点）** | WIP→已合入 这种滞后是硬伤；仓库 private 与否直接决定是否构成公开 |
| 二 | 开关与门控（运行时／编译期、默认值、查询方式） | 权项与说明书都要用，写错等于权项落空 |
| 三 | **有益效果数据（正文一律用本表，旧分支数据只能进脚注）** | 见 §四 数据口径红线 |
| 四 | **首案**技术承重（上位／并列独权骨架、必做的手术） | 权项结构定不下来，胶片和交底书会各说各的 |
| 五 | **第二／后续各案的技术承重（一案一段，不许合并）** | 合并写就分不清哪个特征承的是哪一案的独权 |
| 六 | 现有技术清单与逐件区分理由 | §三 |
| 七 | 市场价值与竞争格局 | 数字必须有出处，二手转述要标 |
| 八 | 侵权可获取性判据 | |
| 九 | 公开状态、在先公开与专利联盟风险 | 申请人自身的在先公开最容易漏；OIN 类风险见 §〇.2 |
| 十 | 撰写红线 | 把本 skill 里与本项目相关的条目落地成具体禁令 |

**FACTS.md 里每一条容易读错的数据，都要就地写清「不能怎么读」。** 例：

> ⚠️ 采样占比 68.88% → 1.52% **不能单独拿来算降幅** —— 改造后编译器把某函数 outline 单独计数为 31.05%，两者合计才是「位图处理由约 69% 降到约 33%」。把 68.88%→1.52% 说成「45 倍」是把编译器的函数拆分当成了性能提升，属错误表述。

这条注释在本项目里救了一次已经上片的错误结论。**没有这层注释，事实底座只是数据仓库，不是口径来源。**

## 二、权利要求红线

> **适用域：默认中国首申、12 个月后走 PCT／美国。** 换司法辖区先重核条号；条号速查表（带核实日期）在 `prefiling-assessment.md` §三。

1. **三件套齐全**：每件写「方法 ＋ 计算机可读存储介质 ＋ 装置」。**理由是够不够得着侵权人，不是费用** —— 方法权项只能抓实施该方法的人，而库形态的软件里芯片厂商与 OS 发行方只是**分发者**，不落入方法权项；装置与 CRM 权项才够得着（进攻路径是指导案例 159 号「方法固化于产品」）。美国侧 37 CFR 1.16(h)(i) 的「3 项独权／20 项总权项」免费额度按件计、三件套正好用满，那是附带好处。
2. **独权范围要说准**：如果主张的是「A＋B＋C 的组合」，就不能在别处把独权说成只有 A。本项目踩过：技术方案页说独权是第 ① 步，现有技术页说是「三条的组合」，创新点页又说是第 ① 步 —— 审查员会当成边界没想清楚。**全篇对独权范围只能有一种说法。**
3. **一个技术特征只能有一个短名**。本项目踩过：同一个创新点在相邻页上叫「向量取位」「向量取出」「批量取位」三个名。凡是要写进权项的特征，先在 FACTS.md 里定名，全篇（含图内文字）照抄。
4. **开源里已有的动作，不单独写进独权**。例：「取最低置位并就地清除」tcmalloc 已用，单独入独权容易被现有技术驳回；它应当作为下位实现落在从属权项。
5. **下位实现不要画成流程的下一步**。框图里 ①→② 若是「种概念」关系而非「先后工序」，实线串联会与权项架构冲突 —— 用虚线并注明「下位实现」。
6. **效果性／意图性表述写了等于没写，但两地依据不同，别混着写**。【中国】效果性／意图性限定不得替代技术特征（依据以现行《专利审查指南》为准，撰写前与代理师确认章节号）；否定式限定下沉（全面覆盖原则，法释〔2009〕21 号第七条）；从属权不得取消母权限定。【美国】intended-use／whereby 类表述在权项解释上**可被忽略、不给专利性权重**（MPEP 2111.04）—— 它是**解释规则**，不是禁止条款。
7. **必做的手术要在 FACTS.md 里列成清单**（如统一位图极性、剥离某个特征让渡给别案），逐案照办、不得遗漏。手术清单的来源是单一性矩阵里标「有重叠」的那几对。
8. **提交号引用要实查**。只存在于废弃分支的 SHA 不能当「本方在先实施」的证据：

```bash
# 退出码 0 = <sha> 是该 ref 的祖先；1 = 不是；128 = sha 不存在
git merge-base --is-ancestor <sha> origin/master; echo "master: $?"
git merge-base --is-ancestor <sha> <PR 的 merge commit>; echo "PR: $?"
```

## 三、现有技术怎么写

> **怎么把检索真的做出来**（三个维度、字段分层、结论怎么写才承重）在 `references/search-method.md`。本节只管怎么写进文档。

1. **「最接近的现有技术」在审查里有唯一指向**。全篇只能有一处不带限定语的「最接近」，其余都要加限定：「同领域最接近的**公开实现**」「**专利文献中**最接近的一件」。
2. **量词分清**：专利文献用「件」，开源实现／源码用「项」。审查员看到「最接近的一件」会先去找公开号。
3. **写它设计上的不足，不写「还差一环」**。「还差一环」是从我们的方案倒推出来的口径，读起来像在给对方挑刺；正确写法是就它自己的设计讲局限（如「位图刻意做成单层、规模封顶，位置数涨上去这条路走不下去」）。
4. **不用「凑在一起」「拼凑」这类词**。「简单拼凑」正是创造性被否的常见理由，等于自己把词递过去。改成「本案主张保护的是这三条的组合 …… 三条相互依赖，少任何一条都退回原路」。
5. **申请人自身的在先公开要主动找**。本项目在检索的第三个维度（开源／学术／社区提案）里发现了项目自身的 Issue，文字层面已提出两个方向 —— 这类件不找出来，后面会被无效程序抓。
6. **载荷性判断必须回到专利原文权项／说明书**，不得采信摘要式转述。
7. **检索未闭环项要如实列出**（付费库未检、某语种未覆盖、某专利族未逐件读完）。一句「未发现相同技术方案」在无效程序里会被逐字拿来打脸。

## 四、数据口径红线

1. **正值表提升**：耗时下降换算成加速倍数或 +%，原口径保留在小字括注。严禁同页正负混排。
2. **同页不得混用倍数与百分比**。`+374%` 其实是 4.7×，与 `4.5×` 并排时会被读成高出一大截。**统一成倍数**。
3. **单位与方向必须写出来**。数值在变小却标着 +96%，不给单位读者判断不了方向。写 `13.26 → 6.76 ns/op`。
4. **合计值不得单独归因**。多项优化一起开出来的分数，标题与副标题都要写明「不单独归因于本案」，否则是全篇最可能被审查员抓的过度主张。（若评审要求删掉这句护栏，**要当面说清删掉的后果**。）
5. **图上必须画出全部构成**。本项目踩过：改造后的占比拆成 1.52% ＋ 31.05%，图上只画了 1.52%、31.05% 留在小字里 —— 视觉上像降了 45 倍、实际只有 2 倍。**读者第一眼取到的数必须是对的。**
6. **两根条的分段口径不同就必须分组标注**（如「改造前按源码行拆」「改造后按函数拆」），否则读者会当成同一套分类去找对应项。
7. **柱状图不许加最小高度**。加了最小高度就把小值画大了。比例悬殊时改**横条**。
8. **定稿前做一遍数字自洽校验**：分段之和 ＝ 总数？倍数 ＝ 前值／后值？跨页同一个数是否一致？本项目踩到过 `11.4×` 与页内读数 `8.28 / 0.73`（＝11.34）除不出来 —— 若倍数来自更精确的原始口径，就把原口径写进小字括注，让除法有出处。

## 五、交底书（docx）

固定七节，逐节写满，不得跳节（详细骨架见 `references/disclosure-skeleton.md`）：

```
1. 专利申请合规检查
2. 缩略语和关键术语
   2.1 缩略语   2.2 关键术语（内部术语／自造词必须解释）
3. 相关技术背景以及最接近的现有技术
   3.1 背景技术
   3.2 与本发明相关的现有技术
       3.2.1 现有技术的技术方案   3.2.2 现有技术的缺点
4. 本发明技术方案的详细阐述
   4.1 所要解决的技术问题        4.2 主要要点概述
   4.3 可应用的系统架构或场景    4.4 产品／售卖形态／侵权取证方式
   4.5 具体实施例（一／二／三）  4.6 主要创新点及其技术效果
   4.7 权利要求要点（全文，方便代理师直接起草）
5. 发散思维
6. 在先公开的现有技术文献信息
7. 自检（逐项确认全部满足）
```

- **§4.7 不是可选项**。胶片的可举证性页与创新点页都把「权项怎么写」推给它（`deck-layout.md` §6.7、`pitfalls.md` B4／E5），漏了就变成三处说法打架。
- **每个实施例都要配完整原理图 ＋ 拆解说明**，不能只有文字。
- **发明人与权属**：职务发明写清「权属归单位，发明人名单待人事与项目侧确认」，不要凭猜写名字。
- **胶片每精简一轮，交底书就要补一张「落脚对照表」**。评审对胶片的删减是单向的，交底书是那些细节唯一的去处（`docx-production.md` §5.1）。
- **反向也要做：拿胶片的每一处修订去交底书查一遍。** 同一个问题在交底书里往往更多、更严重 —— 它更长、写得更早、改的次数更少（`docx-production.md` §5.4）。
- **两份产物的用词要横着对一遍**，各自内部一致不算完 —— 本项目两轮 humanize 独立跑，一边把「端」统一成「侧」、另一边反过来（`docx-production.md` §5.3）。
- **生成与排版全在 `references/docx-production.md`**（参考文档一次性件、`styleId="Table"` 拍平坑、列宽三层算法）。表格承载了七节里的一多半，那张卡不读会毁掉表格，而且只有出图才看得见。

## 六、idea 胶片（pptx）

版式红线全部照 `pptx-pro`。**专利胶片特有的约束全部在 `references/deck-layout.md`**（页面骨架、三个页型的定式、图内字号折算、配色、行距与框内排版、留白怎么收、密度量化）—— 做胶片前把那张卡读完，别凭印象发挥。

随手要记住的四条：

- **基准模板**：`ai-docs/jemalloc/patent-filing/` 下任一案目录里版本号最大的 `build_deck_vN.js` 与同名 pptx。新做一件先渲染它逐页看一遍，按它的页型填内容。**规则以 `deck-layout.md` 的文字为准**，模板只是它的一个实现；两者不一致时是模板还没跟上。
- **只留大标题、不要页脚、正文不许灰字、一页一节**；删了东西就必须重新摊开剩下的（`deck-layout.md` §6.4c）。
- **图内字号按落位反推画布宽度**：`实际 pt = 图内 px ÷ 画布宽(单位) × 该图净宽(英寸) × 72`。内容放不下就删内容，不要缩字号（`deck-layout.md` §6.2）。
- **留白怎么收有固定顺序**：先放大内容 → 再收口卡框 → 最后才平分空档。只做第三步等于白改（`deck-layout.md` §6.4d）。

## 七、术语与人话

中文标点、断行、通用黑话对照表由 `humanize-check` 统一维护，本节只列**专利场景特有**的：

| 不要写 | 要写 | 原因 |
|---|---|---|
| IPC | 每周期执行 N 条指令 | 在专利文件里必然被读成「国际专利分类」 |
| 摘要（指数据结构） | 上层汇总 | 会被读成「专利摘要」 |
| 载荷性 | 是否落入权项范围 | 自造简称，且与侵权判定的正式说法对不上 |
| 固证 / 上树 | 取证 / 切成多级树 | 黑话与自造简称 |
| 授人以柄 | 容易被以现有技术驳回 | 要写成审查后果，不是感叹 |
| 落地形态 | 工程实现形态 | |
| 补货 / 出货 | 线程缓存填充（tcache fill）／批量回收（tcache flush） | 零售业口语，最伤专业感 |
| 回冲 | 回收 | 直译腔 |
| L1D miss | 一级数据缓存缺失 | 未解释缩写 |

其他两条：

- **首次出现的领域术语当场释义**（`slab`、`region`、向量长度 VL……），且释义要出现在**首次使用的那一页**。
- **正文与图内用同一套词**。图里写 `region`、正文写「位置」，读者对不上号。中英写法不同（胶片「尺寸类」／交底书 `size-class`）是合理分工，但**必须在交底书 §2.2 写一句「二者指同一概念」**。
- **上面这张表是用来判断的，不是用来套的**。同一个词在两份文件里的处境可能不同：交底书 §2.2 若已写明「本文『摘要』一词凡指该数据结构」，那处就不必改，改了反而丢掉一个标准术语（`docx-production.md` §5.4）。

## 八、定稿门禁（1～4 缺一不可，5 视情况）

**胶片与交底书各走一遍，别只跑胶片。**

1. `AUDIT=1 OUT=<路径> node build_deck_vN.js` —— 几何审计，六类：`OUTSIDE-CARD` / `OFF-SLIDE` / `DEGENERATE` / `NEGATIVE-BOX` / `LINE-SPACING` / `MISSING-IMG`。
2. `soffice --headless --convert-to pdf` ＋ `pdftoppm -png -r 150` —— **逐页出图目检**。文字出框、换行溢出、箭头没接上、零宽形状消失这几类审计一概查不出，只有出图才看得见。
3. **页底留白量化**（`deck-layout.md` §6.5 的脚本；只量正文页，封面有满幅色块不适用）。
4. **独立 subagent 跑 `/humanize-check`**，视角独立于作者，**胶片一次、交底书一次**。给两边的交待不一样：
   - **胶片**：只改文案不动几何、字数只能减不能增、改完自己重跑审计与出图核对、**评审点名指定的字符串逐条列出并声明不许动**（标题、名称、引用的 prompt 原文 —— 见 pptx-pro §五.2；humanize 的判据再对，也压不过这一条）。
   - **交底书**：语域保持正式（它不是科普文）、**权项部分只许修中文病句与标点**（限定词、「且／或」「至少一项」「包括但不限于」与否定式表述的位置就是权项范围本身，动一个字就是改保护范围）、事实与核实状态原样保留（数字、公开号、commit、法条号、「已核实／待核实」一律不动）。
5. **多视角对账**（评审给了逐条清单时）：起三个独立视角并行 —— ① 逐条对账（做到了／没做到／**做过头了**）② humanize ③ 版式密度，再由一个裁判合并去重。**注意**：workflow 里任一 agent 挂掉，最终 `findings` 可能是空数组 —— **先读 workflow 的 journal 把已完成 agent 的结果捞出来，再下「没问题」的结论**（路径 `~/.claude/projects/<项目slug>/<会话UUID>/subagents/workflows/wf_<id>/journal.jsonl`，别漏了会话 UUID 那一层；找不着就 `find ~/.claude/projects -name journal.jsonl -newermt '-2 hours'`。它是 harness 侧产物，不由 workflow 脚本生成）。

## 九、与评审协作的规矩

1. **「没提到的地方不要动」就是硬约束**。逐条清单来了之后，改动范围严格限定在清单内；清单外的改动只有一种是允许的：**删减造成的硬伤**（如删小标题连带删掉了唯一一处术语约定），而且要在回复里说明为什么补。
2. **删掉护栏要当面讲后果**。评审要求删掉「本案是六项中的一项」这类归因说明时，照删，但要明确告诉他删掉之后这页无法回答什么问题。
3. **参照物先打开再动手**。评审说「用 v4 版本的图」，就去 `git show <v4 提交>:<路径>` 把原件取出来，用 SHA-256 比对确认一致，不要凭印象重画。
4. **仓库有并发改动时先查再改**。本项目遇到过另一个会话重画了同名图并提交，导致「用 v4 的图」拿到的其实是别人的新图。发现并发改动要在回复里点明，并说清自己覆盖了什么。
5. **版本策略**：结构／内容有意义的改动出新版本（v2、v3……）；同一轮内的微调就地改。

## 十一、本 skill 不做的事

- **不出正式 FTO／检索报告**。§〇 与 `search-method.md` 做的是内部预评估与自查检索，不能替代付费库的正式检索报告。
- **不替代代理师定稿**，也不答复审查意见。权项文字最终以代理师与 IP／法务的定稿为准。
- **法条不是本 skill 的事实源**。`prefiling-assessment.md` 的条号表带核实日期，超过半年一律当「待重核」；引用前与代理师确认现行条号与章节号。
- **不做技术方案本身的评审**。方案值不值得做是项目侧的判断；本 skill 只判它能不能构成一件站得住的专利。
- **不生产实测数据**。数据从事实底座取，本 skill 只管口径与表述；缺数据就开口要，不许编。
