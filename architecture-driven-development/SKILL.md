# 架构驱动开发

从需求到验证结果保持可追踪性。先定义边界与契约，再建立可编译、可测试的架构骨架，随后填充行为并完成测试修复闭环。

## 工作规则

- 开始前检查仓库说明、现有架构、构建方式、测试体系和工作区状态；保护用户已有改动，避免无关修改。
- 使用仓库既有语言、框架、目录、命名和测试惯例；除非需求证明有必要，不引入新的框架或抽象层。
- 维护需求清单、实施计划和追踪矩阵。计划中同时只能有一个进行中的步骤。
- 将“端口”理解为模块对外契约，包括 API、接口、函数、命令、事件、消息、文件格式、数据访问抽象和第三方适配边界。
- 仅在缺失信息会实质改变范围、外部契约、数据、安全、兼容性或验收标准时询问用户。记录低风险假设并继续不受影响的工作。
- 每个实现步骤同时交付生产代码和对应测试；先运行最小相关验证，再运行更广回归。
- 不以文档、编译成功或单元测试单独作为完整交付证据。

## 阶段 1：阅读并分解需求

1. 阅读用户请求和相关代码、配置、模式、文档及测试。
2. 将需求拆成 `REQ-01` 格式的原子项。为每项记录：
   - 用户价值与目标行为；
   - 输入、输出、状态、规则和失败行为；
   - 边界条件、兼容性和非功能约束；
   - 可执行或可观察的验收标准；
   - 状态：已确认、合理假设或待决。
3. 识别冲突、缺失决策、依赖、风险和明确不在范围内的事项。
4. 设计模块及端口：为每个模块定义职责、拥有的数据、依赖、禁止承担的职责；为每个端口定义消费者、提供者、请求与响应、错误语义、幂等性、版本和兼容策略。
5. 建立追踪矩阵：`需求 -> 架构视图 -> 模块/端口 -> 实现 -> 测试 -> 证据`。

完成门槛：每个需求都映射到至少一个模块或端口及可验证的验收标准；所有会改变架构方向的疑问均已解决或明确阻塞。

## 阶段 2：生成设计文档

在仓库惯用文档目录中创建或更新设计文档；若无惯例，使用 `docs/design/<feature>.md`。读取 [design-document-template.md](references/design-document-template.md) 并按任务规模裁剪，禁止省略与当前变更相关的章节。

设计文档必须包含：

- 背景、范围、假设、约束和需求追踪；
- 模块分解、端口清单和契约；
- 至少一张可维护的文本图，优先使用 Mermaid；
- 对中大型或跨模块变更使用 4+1 视图：逻辑、开发、进程、物理和场景；小型变更可以合并不适用的视图，但必须说明理由；
- 关键交互的序列图，以及存在复杂生命周期时的状态图；
- 数据、错误、安全、可观测性、性能、兼容性、迁移和回滚设计中适用的部分；
- 测试策略、实施顺序和设计决策。

根据仓库事实审查设计的可实现性。若实现中发现设计不成立，先更新文档和追踪矩阵，再继续编码。

完成门槛：模块职责无明显重叠，依赖方向清晰，端口契约可测试，图与文字一致，实施步骤可独立验证。

## 阶段 3：开发架构骨架和测试模块

按照依赖顺序建立最小可编译、可加载的架构：

1. 创建模块目录、项目或包边界。
2. 定义端口的类型、接口、消息、路由或命令契约。
3. 建立组合根、依赖注入、注册或适配器连接点。
4. 对尚未实现的行为使用显式的未实现错误或最小占位实现，不返回伪造的成功结果。
5. 为每个生产模块建立对应测试模块，并为每个端口建立契约测试或集成测试框架。
6. 添加最小架构测试，验证依赖方向、注册、序列化、路由或端口连通性中适用的部分。

运行格式化、静态检查、编译和骨架测试。修复失败后才能进入内容实现。

## 阶段 4：补充模块和端口内容

按需求切片逐步实现，而不是一次填满所有模块。对每个切片：

1. 标明关联的需求 ID、模块、端口和验收标准。
2. 实现领域规则、应用编排和边界适配逻辑。
3. 同步补充正常路径、边界、错误与回归测试。
4. 保持端口稳定；需要变更契约时先更新设计、影响分析和契约测试。
5. 运行当前模块测试及跨端口集成测试，通过后更新追踪矩阵。

避免在领域模块中泄漏基础设施细节，避免绕过端口直接形成隐藏耦合，避免为未确认的未来需求增加扩展点。

## 阶段 5：测试、诊断和修复

按以下顺序验证，并保存命令、结果和限制：

1. 格式化、lint、类型检查、模式验证或编译；
2. 模块单元测试；
3. 端口契约测试；
4. 模块间集成测试；
5. 关键场景或端到端测试；
6. 与影响范围相称的回归测试。

测试失败时进入修复循环：

1. 使用最小复现定位失败层级和根因。
2. 区分本次缺陷、既有失败、环境问题和测试自身错误。
3. 只修复范围内根因，同时添加或加强能复现该问题的测试。
4. 重跑失败测试、受影响模块测试和必要回归。
5. 重复直到通过；若受权限、外部服务、缺失决策或不可用依赖阻塞，记录证据、已尝试方案和解除阻塞所需条件，不伪造成功。

## 最终验收

交付前：

- 对照追踪矩阵逐项核验所有需求、设计、实现和测试证据；
- 检查差异中是否存在越界修改、秘密、调试代码、静默占位实现或遗漏文档；
- 确认图表仍与最终代码一致；
- 汇报已交付行为、关键文件、验证命令与结果、假设、风险和未验证项；
- 仅当全部必需验收标准均已实现并验证时声明完成，否则准确标为部分完成或阻塞。
